# 系统演进建议

> 当前系统已经跑通「读 → 卡住 → 补讲」。这份文档回答的是：**接下来该往哪里长，以及为什么是这些。**

---

## 一、三条判断标准

在讨论加什么功能之前，先立标准。否则就是列清单。

**1. 数据在哪一层，决定能力上限。**
Agent 现在只看 `dwell_ms` 一个信号，所以它只能判断"快还是慢"。想让它更聪明，**先扩观察维度，而不是先加规则**。规则是判断的产物，信号是判断的原料。

**2. 规则不能绑死具体内容。**
现在 `rules.py` 里写死了 `seg_p08`、`seg_x_example`。做第三章时，这两条规则一行都用不上。**一个不能换章的系统，只能叫 demo。**

**3. 每个功能都要有验证出口。**
教育产品最怕"看起来在教"。必须有一个地方能回答：这孩子到底懂了没有。

---

## 二、最大的问题不是缺功能，是闭环没闭

| 环节 | 现状 |
|---|---|
| 读 | 有 |
| 卡住 | 有，但只看停留时长 |
| 补讲 | 有，3 张牌 |
| 验证 | **半成品**：关卡算了对错，但结果不回流到判断 |
| 回顾 | 没有 |
| 再来 | 没有，关掉页面就是另一个孩子 |

**前三步是在"讲"，后三步才是"教"。**

所以下面所有功能，都服务于把后三步补上。

---

## 三、P0：不做系统就不成立

### P0-1　引入 learner（学习者）

**问题**：`learn_states` 现在挂在 `session` 上。关掉页面就是新孩子，跨章节什么都不累积，"因材施教"无从谈起。

一个教学系统没有"学生"这个实体，是根本性的缺失。

**改法**

```sql
CREATE TABLE learners (
  id          TEXT PRIMARY KEY,
  nickname    TEXT,
  created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

ALTER TABLE sessions ADD COLUMN learner_id TEXT REFERENCES learners(id);
ALTER TABLE sessions ADD COLUMN read_count INTEGER DEFAULT 0;

-- 长期画像，和"本次会话画像"分开
CREATE TABLE learner_profiles (
  learner_id      TEXT PRIMARY KEY REFERENCES learners(id),
  goals           JSON,   -- {"ch02": {"G1": "achieved", "G2": "in_progress"}}
  misconceptions  JSON,   -- {"M2": "triggered"} 跨章累积
  profile         JSON    -- {"fast_skips": 4, "avg_dwell_ms": 3100}
);
```

**关键区分**

| 表 | 回答什么问题 |
|---|---|
| `learn_states` | 这次读得怎么样 |
| `learner_profiles` | 这个孩子是什么样的 |

前端在书架页加一步"你叫什么"（可跳过，跳过就生成匿名 learner，存在 localStorage）。不做登录。

**验收**：读完第 2 章，换第 3 章，agent 在 `assess` 节点能读到第 2 章留下的"G2 未达成"，并因此更早给补充片段。

---

### P0-2　断点续读

**问题**：刷新页面会话就丢。这是体验硬伤，也是"再来"环节的前提。

**改法**：前端把 `session_id` 存 localStorage，启动时先 `GET /sessions/{id}` 恢复。后端已有这个接口，只差前端用起来。

书架页的章节卡上显示：

```
第 2 章 · 10 段
它背下了整本练习册
上次读到第 6 页 · 继续 →
```

**验收**：读到第 6 页刷新，回来还在第 6 页，agent 的状态也没丢。

---

### P0-3　把规则和内容解耦　✅ 已完成

**问题**：这是最该改的架构问题。改造前的规则长这样：

```python
if seg_id == "seg_p08" and dwell < 3500:
    return insert("seg_x_example")
```

`seg_p08` 是第 2 章第 8 段。第三章的第 8 段讲的是别的事，这条规则就废了。

**改法：让"哪一页是关键页"变成数据。**

```sql
ALTER TABLE segments ADD COLUMN is_checkpoint INTEGER DEFAULT 0;  -- 1 = agent 要盯这一页
```

`segments.goal_tag` 已经有了（G1/G2/G3），补充片段也有。所以可以做成**按目标匹配**：

```python
def decide(ctx):
    seg = ctx["seg"]
    if not seg.is_checkpoint:
        return continue_main()

    if ctx["dwell_ms"] < ctx["threshold"]:
        # 找一张"针对同一目标、还没打过"的牌
        hook = pick_hook(goal_tag=seg.goal_tag, used=ctx["used_hooks"])
        if hook:
            return insert(hook)

    return continue_main()
```

**换第三章时，只需要在新内容里标 `is_checkpoint=1` 并写好 `goal_tag`，代码一行不改。**

这是"能不能做多章"的分水岭。

**验收**：新建一个假章节（两段内容 + 一张补充牌），不改 `rules.py`，`/next` 就能正确插入补充牌。

---

### P0-4　让 agent 说人话（半天，性价比最高）

**问题**：现在 `reason` 只给评委看（"p08 只停了 1200ms"）。孩子完全感觉不到"有人在判断我"。

**改法**：后端多返回一个字段。

```json
{
  "action": "insert",
  "reason": "p08 停留 1200ms（<3500ms），判定为快速翻过",
  "say": "你翻得有点快，我再讲一遍。"
}
```

前端在翻页后用一个淡出小气泡显示 2.5 秒，就像有人在旁边轻轻说了一句。

**改动量**：后端 3 行，前端 10 行 CSS。

**但它把 reason 从"调试信息"变成了"产品体验"** ——这是全系统里唯一能让孩子感知到 agent 存在的地方。不做这个，agent 是隐形的。

**验收**：快读时孩子能看到那句解释；慢读时没有。

## 四、P1：决定产品好坏

### P1-1　章末回顾页

**如果只能加一个功能，加这个。**

现在的结尾是"这一章读完了"，等于没有收束。回顾页应该给出：

```
今天你读完了「它背下了整本练习册」

你在第 8 页停了 8 秒 —— 那是这一章最难的地方
你试了 5 道题，它答错了 2 道
你的小本子里有 1 个问题：恐龙为什么会灭绝？

有一件事你带走了：
别用他做过的题，考他会不会。
```

数据全部现成：`learn_states` + `question_book` + `profile.level_tries`。

**为什么它最重要**：它是唯一能把"读了"变成"学到了"的东西，也是家长和评委唯一能看懂的输出。

**实现**：新增一种 `variant: "recap"` 的片段，由后端在 `action=finish` 时动态生成（不入库，实时拼）。

---

### P1-2　扩充观察维度

现在只有 `dwell`。真实可用的信号还有一堆，数据已经在 `events` 表里躺着，规则没用：

| 信号 | 现在怎么处理 | 应该怎么用 |
|---|---|---|
| `bubble_click` | 只记了 goal_tag | 点了气泡但没往下翻 → 说明有疑问，可以主动问一句 |
| `level_try` | 只计数 | 同一道题连错 2 次 → 换个说法，而不是继续加题 |
| 回翻（新增 `back` 事件） | 没有 | 回翻说明没跟上，可以放慢节奏 |
| `ask` 的内容 | 只判超纲 | 问"它是不是坏了" → M2 误区，直接追问 |

**判断原则**：一个信号只有在"能改变 agent 的动作"时才值得采集。不要为了埋点而埋点。

---

### P1-3　第二次读，换一套策略

有了 `read_count` 之后，第二次打开同一章可以做得不一样：

- 已经达成的目标，对应片段缩短停留
- 直接给一张进阶补充牌（比如"如果练习册里有 3+5，它会学成什么样"）
- 结尾问一句"这次你看出什么新东西了吗"

这才是"再来"的意义：**不是重复，是加深**。

## 五、P2：加分项

| 功能 | 价值 | 成本 |
|---|---|---|

## 六、我建议砍掉的

### 已完成：自由对话接大模型

原本建议本期砍掉，团队决定保留。已实现，护栏如下——**这决定了它上台时会不会翻车**：

| 护栏 | 做法 |
|---|---|
| 没配 key 也能跑 | `LLM_ENABLED` 关闭时 `/ask` 回落到人工答案库，功能不缺失 |
| 首字超时 | 4 秒内不出第一个 token 就放弃，回落到安全答案，不让孩子干等 |
| 报错 / 限流 | 任何异常都回落，返回 `via: "fallback"`，前端照常显示 |
| 防跑题 | system prompt 写死：无关问题只回"这个我还答不上来，先记在小本子上" |
| 防成本 | 单会话最多 30 次（`LLM_MAX_ASKS`），超出转人工答案 |

**接口形状没变**：`/ask` 仍是 SSE，只是 `via` 字段会变成 `rule` / `llm` / `offline` / `fallback`，答辩时一眼能看出走的哪条路。

**演示建议**：正常开 `LLM_ENABLED=1` 演示自由对话；网络不稳就临时设 `0`，整章与提问照常可用。

### 砍：教师端后台

理由：一周工作量，收益是"看起来完整"。而**章末回顾页已经能覆盖 80% 的价值**，还更聚焦。

---

## 七、落地顺序

按"地基 → 可扩展 → 出价值 → 提体验"排：

| 顺序 | 做什么 | 时间 | 为什么这个顺序 |
|---|---|---|---|
| 1 | P0-2 断点续读 | 0.5 天 | 最便宜，立刻改善体验 |
| 2 | P0-4 say 字段 | 0.5 天 | 同样便宜，让 agent 可见 |
| 3 | P0-1 learner | 2 天 | 所有"跨章"能力的地基 |
| 4 | P0-3 规则解耦 | 2 天 | 决定能不能做第三章 |
| 5 | P1-1 章末回顾 | 2 天 | 产品价值最大的一步 |
| 6 | P1-2 观察维度 | 2 天 | 让判断真的变聪明 |
| 7 | P1-3 二次阅读 | 1 天 | 锦上添花 |

前四项做完（约 5 天），这个系统就从"一个能演示的 demo"变成"一个能继续长下去的系统"。

---

## 八、一句话总结

> 现在的系统会**讲**，还不会**教**。
>
> 加 learner 是为了"记得住他"，加规则解耦是为了"换个故事还能用"，加章末回顾是为了"让学会这件事被看见"。
>
> 这三件事做完，剩下的都是锦上添花。
